# canonical/ —— 数据模型仍在等，摄取规则已经落地

本目录有两份规范性文档，数据模型（字段、schema）仍然刻意留空——这是**设计决定**，
不是待办遗漏。

| 文档 | 回答什么 |
|---|---|
| [INGESTION.md](INGESTION.md) | 给一堆 bundle，哪些能读、读出来能推出什么结论 |
| [IDENTITY.md](IDENTITY.md) | 一条标记是什么，两次抓取之间怎么知道是同一条 |

两份都不依赖字段清单长什么样，所以现在就能定。

两者分开是因为它们等的东西不一样。摄取规则只依赖 `bundle/v1/` 里已经定死的字段
（`verdict`、`enumeration`、`contiguous`、`status`），现在就能定；而字段长什么样
要等更多真实页面。

**摄取规则等不了**：它决定了解析器会不会把「我们没看」当成「用户删了」，而那个
错误一旦写进 canonical，下游没有任何办法发现。

## 为什么推迟

`canonical/` 是解析器的产出格式。现在就把它定下来，等于**对着十五年间从未见过的豆瓣页面结构建模**——那样产出的 schema，碰上第一张 2011 年的页面就会碎掉。

这不是假想。在一份真实旧档案里可以直接看到 markup 漂移：同一账号的电影列表页，条目容器在

- 2022-12-26、2023-01-27 的抓取中是 `class="item"`
- 2023-12-18、2024-08-11 的抓取中是 `class="item comment-item"`

**仅两年之内、单个用户的档案里就变了一次。** 一个写死选择器的解析器会在这里静默地返回零条目。而由于 WARC 已经把原始页面存下来了，改解析器重跑即可——这正是把「捕获」与「解释」分开的价值。

推迟没有代价，因为两棵树的生命周期是相反的：

| | `bundle/` | `canonical/` |
|---|---|---|
| 谁写 | 抓取工具 | 解析器 |
| 生命周期 | 用户跑过一次就**冻结** | **随时可改** |
| 为什么 | 没法请人家重爬一遍 | 拿着已有的 WARC 重跑解析器不要钱 |

**把这两者当成同一个格式来设计，是本项目最主要的翻车方式。**

## 什么时候开始

原来写的条件是「等 `doubak-extension` 跑通第一批真实档案」。**那个条件已经满足**
（2026-08，五份成链的真实档案）。开始之后先量了一轮，量出来的东西直接改掉了两处
本来要写进模型的假设：

- **`data-cid`（豆瓣自己的标记记录 id）在 2023-12 之前的抓取里根本不存在。** 本来
  打算拿它当记录身份——而它在半份历史档案里是空的。
- **同一个字段在不同媒介下走完全不同的 markup。** 统一选择器量出「游戏 0% 有评分、
  0% 有短评」，改对之后是 51% 与 72%——306 个评分、433 条短评差点被静默丢掉。

所以字段层面还要再量。而摄取与身份两层已经够了。

身份那一层是靠一次**真实的状态迁移**定下来的：五份成链的档案里，有三条标记恰好在
抓取之间从「想看」变成了「看过」，全过程被拍了下来——状态、日期、评分、短评四样
一起换，**只有 `data-cid` 没变**。细节见 IDENTITY.md。

## 已经确定的方向

不必从零开始，以下判断已经定了：

- **canonical 是事件日志，投影是缓存。** 豆瓣只存当前状态，所以朴素的 `(用户, 条目, 状态)` 一行是错的——「在看，且有新评论」和「又看了一遍」都是第二个事件，状态却相同。canonical 建模的是一条上游**可变记录** + 每次观察产生一条**修订**（带 `parser_version`、逐字段摘要，以及指回 WARC 的 `capture_ids`）。事件是**派生视图**。
- **用户编辑追加新事件到 canonical，任何东西都不写投影。** 投影一旦可写，就有了两个真相来源，「无摩擦导出」这个承诺随即作废。
- **只比较同一 `parser_version` 产出的修订。** 否则修一个提取 bug 会让四万条记录看起来像是同时被编辑过。
- **三种时间戳永不合并**：`occurred_at` / `recorded_at` / `observed_at`。豆瓣的 `recorded_at` 在编辑时不变、只在删除重建时变——它是**记录指纹，不是时钟**。
- **canonical 是无损超集。** NeoDB、Letterboxd CSV、Goodreads CSV、ActivityStreams 都是有损的**对外**适配器。绝不以 NeoDB 的格式存储。

## 与 bundle 的接口

解析器从 bundle 读入，唯一需要知道的是 `bundle/v1/` 里定义的东西。有两个字段解析器**必须**用上，否则会出错：

- **`surface`**：同一条内容在 HTML 面和 API 面各存了一份。不区分就会把它们当成两次修订。
- **`enumeration`**：只有 `full` 的路线才允许推断删除；`bounded` 的路线下界以下根本没看过，缺失无法与「没抓到」区分。

另外，`coverage` 中豆瓣声称的数量**不可作为完整性依据**（豆瓣的计数器有时统计于审查之前、有时之后）。完整性看 `crawl_state`。

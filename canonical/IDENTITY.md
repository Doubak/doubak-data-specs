# 一条标记是什么 —— 身份、可变字段、以及怎么知道是同一条

**状态：规范性草案。** 与 [INGESTION.md](INGESTION.md) 一样，这份文档回答的问题
不依赖字段清单最终长什么样。

它回答的是：**豆瓣上的一条标记，在两次抓取之间变了，我们怎么知道那是"同一条变了"
而不是"一条没了、另一条新增"。** 答错的方向是把一次编辑记成一删一增——修订历史随
之作废，而修订历史正是这整个项目的产出。

---

## 1. 一次真实的状态迁移，全程被拍了下来

不是构造的例子。五份成链的真实档案里，有三条标记恰好在抓取之间发生了状态迁移。
取其中一条（电影 `36838707`）：

| 观测于 | 状态 | 页面上的日期 | 评分 | 短评 | `data-cid` |
|---|---|---|---|---|---|
| `20260801` 抓取 | **想看** | 2026-07-18 | — | 能上6分我觉得都是国产好片 | `4891953008` |
| `20260804` 抓取 | **看过** | **2026-08-01** | **4** | 确实还不错，剧情挺有趣的…… | `4891953008` |

**除了 `data-cid`，字段全变了。** 状态、日期、评分、短评，四样一起换。

如果身份取 `(作品, 状态)`，这就是"想看里少了一条 + 看过里多了一条"——两条记录，
没有历史。如果身份取 `data-cid`，这是一条记录的两次修订，中间发生了一次状态迁移。
**后者才是真的。**

## 2. `data-cid` 是身份，但**不能设为必填**

### 2.1 它稳

跨五份档案统计所有被观测到 ≥2 次的标记：

```
data-cid 一致  105 条
data-cid 变了    0 条
```

包括上面那条跨状态迁移的。

### 2.2 但它经常不在

| 情形 | 有 `data-cid` 吗 | 实测 |
|---|---|---|
| 电影 / 书 / 音乐 / 舞台剧，2023-12 之后抓的 | 有 | 稳定 |
| **游戏**（任何时候） | **没有** | 601 条全都没有 |
| **任何媒介，2023-12 之前抓的** | **没有** | 前代档案里 3078 条全都没有 |

游戏另有一个等价物，在删除按钮上：

```html
<a class="js-remove-collect" data-url="/j/ilmen/thing/37364867/interest">删除</a>
```

实测 601 条游戏标记**全都有**，比作品链接更可靠——作品被豆瓣删掉之后，标题变成
「未知游戏」、连 `<a>` 都没有了，而这个属性还在。

### 2.3 所以身份是分层的

解析器**必须**按以下顺序确定身份，并**必须**记下用的是哪一层：

1. `data-cid`（或游戏的 `ilmen thing id`）—— 上游自己的记录 id，最可信
2. `(账号, 媒介, 作品 id)` —— 退化键。**它把状态迁移正确地识别为同一条记录**，
   这正是上面那个例子需要的
3. 都没有 → 只能记为一次观测，**不得**与任何既有记录合并

第 2 层的代价要写清楚：同一个作品被标记、删除、又重新标记，退化键会把它们并成
一条。这是**可接受的**——两次标记之间的空档，退化键下无法区分"删了又加"与"一直
都在"，而错误方向是少报一次删除，不是凭空捏造一次。

### 2.4 两层混在一起时：**必须归并，不得各成一条**

上面那三层说的是「一次观测怎么定层」。还差一句，而缺了它会出事：

> 同一条标记的不同观测**分属不同层**时，它们仍然是同一条记录。

这不是罕见情形，是**必然**情形：照 §2.2 那张表，2023-12 之前抓的页面一律没有
`data-cid`。所以只要一个目录里同时有那条线两侧的档案——增量抓了两年、或者从别的
工具导进来一批老页面——每一条跨越那条线的标记都会遇到这件事。

把两层做成两个不相交的键空间，后果是一条标记裂成两条记录。实测（前代工具
2022-12 → 2024-08 的档案）：**2526 个作品出了 4050 条标记**，修订史被劈成两半。
失败的形状是最坏的那一种：不报错，而且**看起来像数据变多了**。

归并规则，用退化键当「这是哪个作品」的锚点：

1. 先在没有 `data-cid` 的年代见过、后来拿到了 → **把那条记录搬到上游键上**，
   不另起一条。
2. 先有上游 id、后来的观测没有 → 跟着已经确定的键走。
3. 同一个作品先后出现**两个不同的**上游 id → **不合并**。那是「标了、删了、又
   重新标」，是只有 `data-cid` 给得出的信息，正是它比退化键强的地方，归并时把它
   丢掉等于把一次真实的删除重标抹成一次编辑。

**搬过去之后 `identity_layer` 仍然写 `degraded_key`。** 它回答的是「这条记录的
身份最弱靠到了哪一层」，而早年那几次观测确确实实是靠退化键认回来的。改写成
`upstream_id` 会把那件事掩盖掉——而读者判断「这些修订真的是同一条记录吗」时，
要看的正是最弱的那一环。

## 3. 页面上那个日期**会动**，它不是"这件事什么时候发生的"

上例里，同一条记录（`data-cid` 不变）的日期从 `2026-07-18` 变成了 `2026-08-01`。

所以列表页 `<span class="date">` 的语义是**"这条标记到达当前状态的时间"**，不是
"这条记录被创建的时间"。它跟着状态迁移一起动。

这直接决定了三种时间戳怎么填（规范里那条"三种时间戳永不合并"）：

| | 填什么 |
|---|---|
| `observed_at` | 抓取那一刻。来自 `index.ndjson`，永远可得 |
| `recorded_at` | 页面上那个日期。**属于这一次修订，不属于记录** |
| `occurred_at` | 通常 **null**。豆瓣不记录"你实际什么时候看的" |

把页面日期当成记录的创建时间，会让每一次状态迁移看起来像"记录被删了重建"。

## 4. 广播是同一条记录的**第二个、且冻结的**观测

上例那条 想看 短评，在豆瓣的标记页上**已经没有了**——它被 看过 的短评覆盖了。
但它在广播里还在：

```
想看 · 2026-07-18 12:44:56 · 能上6分我觉得都是国产好片
```

三点，每一点都有用：

1. **它证实了 CLAUDE.md 里那个论断**：广播发布后不可编辑，因此是"这条评论在那一刻
   说了什么"的带日期快照，也是**唯一能发现首次抓取之前发生过的编辑**的来源。
2. **它的时间精度更高。** 列表页只到天（`2026-07-18`），广播到秒
   （`12:44:56`）。同一条记录的两个观测，精度不同——合并时不得用低精度的覆盖高精度的。
3. **它是独立取得的。** 广播路线与标记列表路线互不依赖，所以它们对同一条记录的说法
   一致与否，是一个免费的自检。

因此：广播里的标记事件**必须**能与标记记录关联起来（广播的 `data-object-id` 就是
作品 id），但**不得**当成另一条记录。

## 5. 由此确定的模型形状

```
记录 (record)
  身份     data-cid / ilmen id ／ 退化键 (账号, 媒介, 作品)
  身份层级 必须记下用的是哪一层

  修订 (revision) ── 每次观测一条，永不覆盖
    observed_at    抓取时刻
    parser_version 只与同版本的修订比较
    capture_ids    指回 WARC
    source         标记列表页 ／ 广播 ／ …（精度与可信度不同）
    字段快照       状态、日期、评分、短评、标签…（每个字段单独摘要）
```

**事件是派生视图，不是存储。** 「2026-08-01 从想看变成看过」是比较相邻两条修订
算出来的，不是写死的一行。这样抽取器改好之后重跑，事件会跟着变对；写死则会永远
留着当初那个错误。

---

## 6. 这份文档没有回答的

- **字段清单本身**。每种媒介可用的字段差别很大（电影 63% 有评分，音乐 100%，
  书 34%），且各走各的 markup。还要再量一轮。
- **`intro` 那个无标签的 `/` 分隔串**（导演、演员、国家、片长、类型全混在一起）
  要不要在解析时拆开。倾向**不拆**：原样存字符串，拆解归 enricher——理由与
  "解析器不许猜语言标签"相同，猜错了在源页面消失之后无法挽回。

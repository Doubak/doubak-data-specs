# canonical/v1 —— 解析器的产出格式

**状态：草案，`canonical/1.0`。** 只覆盖**标记**与**作品**两类，那是目前唯一被真实数据量透的部分。广播、日记、评论沿用同一套「记录 + 修订」骨架，随后补上。

```
marks.ndjson       一行一条标记（用户写的）      mark.schema.json
subjects.ndjson    一行一个作品（目录数据）      subject.schema.json
```

设计依据在上一层三份文档里，此处不重复：
[INGESTION.md](../INGESTION.md)（哪些档案能读、能推出什么）、
[IDENTITY.md](../IDENTITY.md)（怎么知道是同一条）、
[FIELDS.md](../FIELDS.md)（能拿到什么、哪些不该拆）。

## 三个自己做的决定

这一层是**设计**，不是测量——前面每条结论都是数出来的，下面这三条不是。

### 1. 修订只在内容变了时追加，不是每次观测追加

实测 2933 条标记 × 6 次抓取 ≈ 17600 次观测，其中**真正的编辑只有 3 次**。按观测追加会让 99.98% 的行是噪音，而「这条什么时候变过」——canonical 存在的理由——反而要从噪音里筛出来。

观测本身没有丢：每条修订带 `observations` 数组，「我们在 T 时刻看到它还是这样」照样可查，而且每一条都能指回 WARC 里的具体字节。

判据是**逐字段摘要**，不是整条摘要——否则改一次评分会让短评也看起来被重写过。

### 2. 一行装下一条记录的全部修订，不拆成两个文件去 join

这个项目选 NDJSON 而不是 protobuf 的理由是「用 `jq` 就能查，永远」。拆成 `records` + `revisions` 两个文件之后，回答任何问题都要先 join，那句承诺就废了一半。

```sh
jq 'select(.subject.id=="1292052")' marks.ndjson    # 这条标记的全部历史
```

修订数量本来就少（实测多数记录只有 1 条），嵌套没有体积问题。

### 3. 用户写的东西与作品目录数据分两个文件

CLAUDE.md 里的硬性推论：两者的留存期限、删除语义、法律处境都不同。混进一张表，「导出你自己的数据」就说不清导的是什么。

同时它也决定了**哪一边是缓存**：作品数据随时可以删掉重新解析（豆瓣还在就能重抓），用户的标记删了就没了。

## 刻意没有的东西

- **事件表。** 「2026-08-01 从想看变成看过」是比较相邻两条修订算出来的，不存。存下来的话，抽取器改好之后事件不会跟着变对，会永远留着当初那个错误。
- **投影 / 当前状态视图。** 那是缓存，归站点生成器。canonical 里一旦有了可写的当前状态，就有了两个真相来源。
- **完整性字段。** 与 bundle 同理：完整性证据在 `crawl_state` 的连续性证明里，不在这里复述一份可能过期的结论。
- **任何需要推断才能得到的字段。** 拆 `raw_meta`、猜语言标签、补外部链接——全部归 enricher，它的产出带 `source` 与置信度且可以重跑。

## 与 bundle 的生命周期相反

| | `bundle/` | `canonical/` |
|---|---|---|
| 谁写 | 抓取工具 | 解析器 |
| 生命周期 | 用户跑过一次就**冻结** | **随时可以整个删掉重新生成** |
| 改错的代价 | 不可逆 | 重跑一遍 |

所以这里的版本递增比 bundle 那边随意得多。**真正不能改的东西都在 bundle 里**——这正是当初把两者分开的全部意义。

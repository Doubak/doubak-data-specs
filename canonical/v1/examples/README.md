# examples/ —— 从真实档案算出来的，不是手写的

## `mark-status-transition.json`

一条真实的标记，跨五份成链档案被观测了 **6 次**，产出 **2 条修订**。

电影《…》（`36838707`），2026-07-18 标了「想看」，2026-08-01 改成「看过」。整个迁移过程恰好落在两次抓取之间，被完整拍了下来——这也是 [IDENTITY.md](../../IDENTITY.md) 里身份规则的原始依据。

生成方式：读 `20260801`…`20260807` 五份档案的 WARC，逐条抽取、算摘要、按内容分组。**没有一个值是手写的。**

### 看三件事

**① 6 次观测压成了 2 条修订。**

```
wish  2026-07-18  无评分  「能上6分我觉得都是国产好片」   ← 1 次观测
done  2026-08-01  评分 4  「确实还不错，剧情挺有趣的…」   ← 5 次观测
```

后 5 次抓取看到的内容完全一样，所以没有产生 5 条噪音行，而是延长了同一条修订的 `last_observed_at` 并往 `observations` 里追加。「我们在 T 时刻看到它还是这样」照样可查，而且每一条都指回具体的 `capture_id`。

**② 逐字段摘要一眼就能看出边界在哪。**

两版之间：

```
变了     status · marked_at · rating · comment · tags
没变     raw_meta
```

变的五个全是**用户写的东西**，没变的那个是**作品目录数据**。整条算一个摘要的话，这个区别就没了——而它正是「用户内容与目录数据不能同表」那条规则的可见形式。

（也因此 `raw_meta` 严格说不属于标记。它留在这里只是作为「那一行当时长什么样」的观测记录，权威版本在 `subjects.ndjson`。）

**③ 那条 想看 短评在豆瓣上已经没有了。**

它被 看过 的短评覆盖了。这份档案是它仅存的两个地方之一——另一个是广播（发布后不可编辑，还带秒级时间戳 `2026-07-18 12:44:56`）。

这就是整个项目要买的东西：**不是"我标了什么"，而是"我当时说了什么"。**

### 还没有的

一个能跑的参考解析器，以及 `bundle/v1/tests/` 那样的反例套件。schema 目前只被结构性检查覆盖（能解析、`$ref` 不悬空）。

## `subject-cdn-shard.json`

一个真实的作品（游戏《神秘海域3》，`11540976`），跨 2022-12 → 2026-09 被观测了 **6 次**，产出 **2 条修订**。它同时演示了 `cover_url` / `cover_url_key` 那条规则的**两半**——该合的合了，该分的还分着。

生成方式：拿全量 28 份档案跑一遍解析器，取出这一条，只把 `parser_version` 换成示例值。**没有一个值是手写的。**

### 换在 `canonical/1.1` 之前，这里是三条修订

```
[0] 2022-12-27              https://img1.doubanio.com/lpic/s28047727.jpg
[1] 2023-12-18 → 2024-08-11 https://img3.doubanio.com/lpic/s28047727.jpg   ← 凭空多出来的
[2] 2026-07-31 → 2026-09-04 https://img3.doubanio.com/lpic/s28418243.jpg
```

`[0]` 与 `[1]` 之间，**唯一的差别是 img1 还是 img3**——路径一模一样，也就是同一张图。其余五个字段（标题、又名、info、raw_meta）一字未动。全量档案里这样的修订有 **111 条**。

### 现在是两条，而**该留的那条还在**

```
[0] 2022-12-27 → 2024-08-11  cover_url_key = …/lpic/s28047727.jpg   3 次观测
[1] 2026-07-31 → 2026-09-04  cover_url_key = …/lpic/s28418243.jpg   3 次观测
```

`[1]` 是**真的换了封面**（`s28047727` → `s28418243`，图片 id 变了），所以它照旧是一条修订。这一条比「少了 111 条」重要得多：一条只会合并的规则，把 `cover_url` 从 `fields` 里整个删掉也能做到，而那是真的丢数据。

### 看三件事

**① `cover_url` 没有摘要，`cover_url_key` 有。**

```
fields    aliases · cover_url · cover_url_key · info · raw_meta · title
digests   aliases ·             cover_url_key · info · raw_meta · title
```

一个字段没有摘要，含义是**它不参与修订判定**。这是个决定，不是漏算——而两者在数据上长得一模一样，所以 `validate.py` 会核对这组键，多一个少一个都报错。

**② `[0]` 留的是 `img1`，不是最后看到的 `img3`。**

分片变了而海报没变时不开新修订，于是这一条留着的是**该修订开张时**看到的那个值。这是对的：一条修订的 `fields` 就是「`first_observed_at` 那一刻页面这么说」，为一个字段破例，读者就会读错另外二十个。最新那个原始值一个字节都没丢——它在 WARC 里，`observations` 里的 `capture_ids` 直接指得到。

**③ 三次观测压成了一条修订，而观测一次没少。**

`[0]` 的 `observations` 有三条，分别来自 2022-12、2023-12、2024-08 三份档案。「我们在 T 时刻看到它还是这样」照样可查，而且每一条都指回具体的 `capture_id`。

### 为什么不干脆把主机改写掉

因为**证不了**。档案里没有任何一条路径被从两个主机各抓过一次（11997 条资源捕获 / 3108 条路径 / 0 条），所以「几个分片提供的字节完全相同」这句话本地无法证实。把 `cover_url` 改写成某一个固定分片，就是在做一个没有证据的断言。

**事实与索引并存，索引不覆盖事实**——与 bundle 的 `url` / `url_key` 是同一条规矩，连理由都一样。

# doubak bundle 格式规范 v1

**当前 spec_version: `bundle/1.2`** ｜ 状态：草案 ｜ 2026-08-07

本目录描述**大版本 1 这一整条线**。读者接受任何 `bundle/1.x`；已经写下的 `bundle/1.0` 档案仍然合法，不需要、也不可能重抓。

本文是规范性文本。JSON Schema 文件是它的机器可读形式；两者冲突时**以本文为准**。

---

## 1. 范围

bundle 是**抓取工具的产出容器**。它描述抓取行为——抓了哪个 URL、为什么抓、抓到的东西可不可信——而**不描述抓到的内容**。它不需要知道任何豆瓣语义：没有「电影」「评分」「看过」这些概念。理解内容是解析器的职责，用的是另一棵独立版本化的格式树（`canonical/`，见 §11）。

### 1.1 为什么这份规范必须一次做对

bundle 是**不可逆步骤的产物**。用户跑完一次抓取，写下去的东西就是他永远拥有的东西——没法请人家重爬一遍，源站的那一页可能已经不在了。

因此本规范的取舍原则是：

> 事后能从 WARC 重新算出来的，都是可选的；事后算不出来的，第一版就必须有。

### 1.2 术语

「**必须**／**不得**」为强制要求，违反即不符合本规范。「**应当**」为强烈建议，偏离需有明确理由。「**可以**」为许可。

## 2. 文件布局

一个 bundle 是一个目录：

```
doubak-bundle-<bundle_id>/
├── README.txt                         必须
├── manifest.json                      必须
├── index-<bundle_id>.ndjson           必须
├── checkpoint.json                    未完成时必须，已完成时不应存在
├── data-<bundle_id>-00001.warc.gz     用户范围的页面与 API 响应
├── assets-<bundle_id>-00001.warc.gz   用户上传的二进制资源
└── catalog-<bundle_id>-00001.warc.gz  作品条目详情页与目录缩略图
```

### 2.1 段前缀表示留存等级，不是媒体类型

| 前缀 | 内容 | 等级 |
|---|---|---|
| `data-` | 广播、标记列表、自己的日记／影评／读书笔记 | **神圣**——源站没了就没了 |
| `assets-` | 用户上传的图（相册、正文内嵌） | **神圣**——同上 |
| `catalog-` | 作品条目详情页、目录缩略图 | **缓存**——源站还在就能重抓 |

这个划分直接来自项目架构中「什么是神圣的、什么是缓存」的判断：目录数据被明确归类为缓存。

实测依据：在一份真实旧档案里，作品条目详情页占 **90.3%** 的体积（692 MB / 766 MB）。把它们单独成段，意味着**「丢掉九成体积」退化成一次 `rm catalog-*`**——不需要任何工具解析内容，也不会碰到档案里不可替代的那部分。

**但「可丢弃」必须说清代价。** `catalog-*` 里的作品元数据是**离线重新生成完整站点的必要输入**：架构要求「丢掉所有派生存储、从捕获重建，必须离线完成、零网络请求」，而列表页只有标题、年份、评分和缩略图，不足以渲染作品页。

所以准确的表述是：

> `catalog-*` **可以丢**——你保住了自己写下的一切；
> 你失去的是**离线重建完整站点**的能力（作品页会退化成只有标题年份）。
> 源站还在时可以重抓，源站没了就补不回来。

这与 `data-* / assets-*` 的区别仍然成立：那两者**任何时候都补不回来**。

段文件大小上限由生产者决定，本规范不作强制。**建议 256 MB**——足够小，低配机器处理得动；足够大，不至于产生几千个文件。

### 2.2 README.txt

**必须**存在，**必须**为中英双语纯文本，且**必须**说明：这是什么、各文件的作用、用什么工具打开 WARC、完整规范在哪里。

它不是文档，是**档案的一部分**。本项目的目标读者包括「2040 年偶然拿到这个目录的陌生人」，那时项目本身可能早已不在。成本几乎为零，收益是这份档案还有没有人能解读。

## 3. 标识符

```
bundle_id  := <UTC 紧凑时间戳> "-" <6 位小写十六进制随机>
              20260728T101500Z-a3f9c1

capture_id := <bundle_id> "#" <序号，零填充到至少 6 位>
              20260728T101500Z-a3f9c1#000042

段文件名   := ("data" | "assets" | "catalog") "-" <bundle_id> "-" <5 位零填充> ".warc.gz"
```

### 3.1 段文件名必须内嵌 bundle_id

每次抓取产出一个**全新的 bundle**，**不得**覆盖或修改任何既有 bundle。段文件名内嵌 `bundle_id`，使得用户把十次抓取的文件全倒进同一个目录时，也不会有任何一个文件互相覆盖。`bundle_id` 以时间戳打头，因此按字典序排序即按时间排序。

### 3.2 序号空洞合法，重复非法

`capture_id` 的序号**必须在写入之前分配**。这样崩溃只会留下**空洞**（某个序号没被用上），而不会留下**重复**。

- 校验器**不得**因序号空洞而报错。
- 校验器**必须**因序号重复而报错。

### 3.3 序号零填充到「至少」6 位

**不是恰好 6 位。** 固定 6 位意味着单个 bundle 最多 999999 次捕获——对一个同时抓图片和作品详情页的重度用户，这并非遥不可及，而撞上限的后果是序号回绕、`capture_id` 重复，正是 §3.2 明令禁止的。

放宽的代价只是：超过 100 万条之后，字典序排序不再等于数值排序。按数值排即可，无实际影响。

## 4. WARC 约定

WARC **必须**保持原味：**不得**添加任何私有扩展头。pywb、ReplayWeb.page 等既有工具必须能不加改造地打开这些段文件。所有 doubak 专有元数据一律放在 `index.ndjson`。

- 每条 WARC 记录**必须**压缩为**独立的 gzip member**。这样每条记录可单独定位与解压，并且**撕裂的文件尾部可被检测**（见 §8.2）。
- 每个段文件**应当**以一条 `warcinfo` 记录开头。
- `WARC-Record-ID` **必须**为 `urn:uuid:` 形式，并按 WARC 规范用尖括号包裹（`<urn:uuid:...>`）。`index.ndjson` 中存的是**不带尖括号**的裸 URI。
- WARC 内部的摘要**应当**沿用 WARC 惯例（`sha1:` + base32），以兼容既有工具。本规范自身的文件完整性校验使用 SHA-256（小写十六进制）。

## 5. manifest.json

见 `manifest.schema.json`。以下只解释规范意图。

### 5.0 `status` 说的是「生产者收尾了」，不是「全都抓到了」

三个取值：`in_progress` / `complete` / `aborted`。`in_progress` 与 `aborted` 时
`checkpoint.json` **必须**存在。

**`complete` 不是完整性声明。** 它只表示生产者刻意结束了这次抓取并写下了 manifest。
完整性证据全部在 `crawl_state` 的连续性证明里（§5.4），`status` 不承担那个职责。

这个区分不是文字游戏。生产者**可以**在存在已知缺口的情况下写 `complete`——最常见的
情形是：某个叶子条目（一个作品详情页）反复抓不下来，而用户看过之后决定「就这样收尾」。
那是一个合理的人的决定，规范不该逼他把整份档案标成 `aborted`，因为 `aborted` 意味着
「还能接着抓」，而他恰恰是决定不接着抓了。

但此时：

- `crawl_state[].gaps` **必须**如实记录每一处缺口（缺口本来就「不得静默」）
- 该路线的 `advanced` **必须**为 false

于是下游读到的是一份自洽的东西：这次抓取结束了，而且它明确告诉你哪里有洞。**读者
不得把 `status: complete` 当作「没有洞」的依据**——要判断那个，只能看 `crawl_state`。

### 5.1 三个不可恢复的字段

CLAUDE.md 指出有三件事必须在第一天就对，因为它们事后无法恢复。本规范再补两个，理由相同。

| 字段 | 位置 | 为什么不可恢复 |
|---|---|---|
| `spec_version` | manifest | 不知道按哪版规范写的，就无法可靠解读 |
| `coverage` | manifest | 页面当时声称的数字，事后源站一变就再也读不到 |
| `intent` | index 每行 | 一份列表的第 7 页，事后无法区分它当初是「看过」还是「想看」的第 7 页 |
| `surface` | index 每行 | 同一条内容在 HTML 与 API 两面各存一份，不标注就会被误认为两次修订；`asset` 则标明这根本不是页面（见 §6.6） |
| `capture_fidelity` | index 每行 | 这条记录到底是不是原始字节，事后无从判断（见 §7.4） |

### 5.2 `timezone_assumption`

豆瓣页面上的时间**不带时区**（如 `title="2026-07-26 12:34:00"`）。几乎可以肯定是服务端的北京时间，但这是**推断**。

因此：所有解析出的时间戳**必须**带显式时区偏移（RFC 3339），同时原始字符串**必须**原样保留在对应的 `*_raw` 字段，而所用的假定**必须**记入 `timezone_assumption`。

将来若假定被推翻，可据原始字符串对存量重新解析。**不得**静默转换。海外时区的用户若缺此字段，水位线可能整体偏移数小时。

### 5.3 `coverage` —— 观测，不是证明

> **豆瓣的计数器不可信，任何情况下都不可作为完整性判据。**

豆瓣存在多套审查／屏蔽机制，其计数**有时统计于审查之前、有时统计于审查之后**。因此「页面说 1234，我抓到 1234」这件事**不能**推出「档案完整」。

#### 实测证据

在一份真实档案（2022-12 至 2024-08，同一账号，20 个批次）中观测到：

| 路线 | 页面声称 | 实际渲染 | 差值 |
|---|---|---|---|
| 电影／看过 | 1157 | 1157 | **0** |
| 游戏／玩过 | 293 | 288 | **−5** |

**同一次抓取、同一时刻、同一工具**——电影分毫不差，游戏差 5 条。而且游戏的缺口**不在末页，在列表中间**：第 7、14、17 页各只渲染出 14、14、13 条，而分页槽位是 15 条。这正是「条目被计入总数、却在渲染时被抑制」的指纹。

该偏差**可复现且随时间增长**：2022-12 为 −3，2023-01 为 −3，2023-12 为 −5，2024-08 为 −5。不是抓取抖动。

关键推论：**你无法在事先不知道答案的情况下，判断哪个分类的计数可信。** 若拿它当完整性闸门，会同时犯两个错——把电影**误判为完整**（它同样可能有被抑制的条目，只是你看不见），并让游戏**永远重试**。

由此还得出两条对生产者的强制要求（§6.5）。

本规范据此做了两个决定：

1. `coverage` **不提供** `completeness`、`reconciled` 之类字段。**不存在的字段无法被误用**——这比在文档里写一句警告可靠得多。校验器**必须**在发现这些字段时报错。
2. 差值字段命名为 `delta` 而非 `discrepancy`：它是一个差值，不是一个错误。

**那为什么还要记？** 两个理由：一是事后不可恢复；二是它有取证价值——`claimed_count` 大于 `captured_count` 可能意味着**豆瓣的计数器知道一些它不肯展示给你的条目**。这个差值是**线索**，不是判决。

完整性的证据来自别处：见 §5.4。

`claimed_count` 为 `null` 与为 `0` 是严格不同的两件事：`null` = 不知道，`0` = 确实没有。

`claimed_count` 非 null 时，`claimed_source` **必须**指向读出该数字的那条捕获。这让「声明页本身也要入 WARC」从一句约定变成了机器可校验的要求：校验器可以顺着指针回到 WARC 里那张页面。没有它，`claimed_count` 只是一个无从核实的数字。

### 5.4 `crawl_state` —— 抓取存档信息

既然计数器不可信，**完整性的唯一依据是抓取过程自身的结构化证明**：是不是从最新一条连续地、无缺口地走到了预定的下界。

#### 5.4.1 两个边界

- **`floor_time`（下界）**：本次往回抓到哪儿为止。首次抓取为 `null`（抓到最早）；增量抓取取上次的 `high_water_time`。与下界比较**必须**使用闭区间（`<=`）：宁可重复，不可遗漏。
- **`high_water_time`（上界／水位线）**：本次抓到的最新一条的时间，成为下次的下界。

水位线存的是**时间值**，**不得**存条目 ID 或页码——任何条目都可能被删除，ID 锚点会凭空消失。跨会话**必须**按内容重新定位，**不得**相信保存下来的页码。

#### 5.4.1.1 `low_water_time` —— 区间的另一端

可选。本次抓取见到的**最旧**一条的时间。

它**不是**水位线，不参与增量判断（那是 `high_water_time` 的事）。它回答的是另一个
问题：**这次抓取覆盖了哪一段**。列表是新→旧翻的，所以这一端就是走到了多早。

两个用处，都很实际：

1. 抓取结束之后，界面上还能说出「这次覆盖了 2023-02-04 → 2025-05-05」。只有上界的话，
   那句话说不出来——而它是一次抓取最容易被问到的总结。
2. 多份档案拼接时，能不重新解析 WARC 就看出各自覆盖的区间，从而发现中间有没有整段没抓。

为什么值得存：抓取时它本来就算出来了（每观测一页更新一次）。扔掉之后想知道，就得把全部
WARC 重新解析一遍，而那要用到抓取当时的选择器——豆瓣改版之后那些选择器可能已经对不上了。

#### 5.4.2 核心不变量

> **`advanced` 为 `true`，当且仅当该路线从最新一条连续无缺口地走到了 `floor_time`。**

即：`advanced: true` **必须**蕴含 `contiguous: true`、`gaps: []`、`high_water_time != null`。

中途暂停、被风控打断、用户放弃——`advanced` **必须**为 `false`。已抓到的数据照样留在 WARC 里（不浪费），但下次仍从旧下界重走。

**重复是免费的，空洞是永久且不可检测的。**

会话内的中断由 checkpoint 负责续抓，不需要重走；只有整场放弃才会重走。

#### 5.4.3 `enumeration` 决定下游有没有资格推断删除

| 取值 | 含义 | 下游可否推断删除 |
|---|---|---|
| `full` | 从头到尾完整枚举了整份列表 | **可以**。「上次有、这次没有」是有意义的信号 |
| `bounded` | 只走到 `floor_time` 就停了 | **不可以**。下界以下根本没看，缺失无法与「没抓到」区分 |

这必须显式写进数据，**不得**留给下游去猜。猜错的方向是**静默地把没删的当成删了**，而且事后无从发现。

**不变量：`floor_time` 非 null 的路线，`enumeration` 必须是 `bounded`。**

这一条不是推论，是硬要求，校验器会拦。因为它在真实档案里被违反过，而违反的方式很自然：`enumeration` 容易被实现成**路线定义上的静态常量**——标记列表写死 `full`，理由是「整份列表从头走到尾」。那句话只对**首次**全量成立。链上一旦有了下界，这条线读到下界就停，下界以下这次压根没看，可字段还写着 `full`：

```
interest.movie.collect   claimed_count=1336   captured_count=15
floor_time="2026-08-02T00:00:00+08:00"        enumeration="full"    ← 自相矛盾
```

下游拿这份增量与那份首次全量做差，会得出「用户删了 1321 条看过」。判据就在同一个对象里（`floor_time` 就摆在旁边），所以没有任何理由让这种矛盾流出去。

反过来不是错误：`floor_time` 为 null 而写 `bounded` 是合法的（比如因别的原因提前停了）。**保守方向是 `bounded`**——多报一次 `bounded` 只是少一个删除信号，多报一次 `full` 是凭空捏造删除。

由此：广播类的时间线路线通常是 `bounded`（首次全量抓取除外）；标记类列表**只有首次**是 `full`，此后每一次增量都是 `bounded`。

### 5.5 链 —— 增量抓取的语义

每次抓取产出一个**全新的 bundle**，绝不覆盖既有 bundle。`previous_bundle_id` 把它们
串成一条链。这一节规定链是什么、以及它坏掉时会怎样。

#### 5.5.1 下界按**路线**选，不按 bundle 选

某条路线的下界，取自**最近一份「这条路线 `advanced: true`」的 bundle** 的
`high_water_time`。

不能简单地用「上一份 bundle」：`advanced` 是逐路线的，上一份里某条线可能因为有缺口
或被打断而没能推进水位线。那时这条线必须继续往回找，找不到就没有下界（从头重走）。

于是同一次抓取里，**不同路线的下界可能来自不同的 bundle**。所以每条路线都要记下
自己的来源：

```
crawl_state[].floor_time             这次往回抓到哪儿
crawl_state[].floor_from_bundle_id   这个下界取自哪一份
```

一个真实的例子：某份 bundle 的广播 `advanced: true`，而作品详情页因为一次中断留下
缺口、`advanced: false`。下一次增量抓取里，广播的下界来自这一份，作品详情页的下界
则要继续往前找——或者压根没有。

#### 5.5.1b 基准必须是**同一个账号、同一个用户名**

数字用户 ID 不同就是别人的档案，**不得**当基准——那会让生产者以为某段时间已经抓过，
而实际抓的是别人的。判错的方向是**漏抓**。

数字 ID 相同但**用户名变了**，同样**不得**接着抓。这一条需要解释，因为下界本身没有
问题（它是个时间，改名不影响它）。断掉的是别的东西：豆瓣的每一条个人路线 URL 里都
嵌着用户名——

```
https://www.douban.com/people/<用户名>/statuses?p=1
https://movie.douban.com/people/<用户名>/collect
```

改名之后新抓取的 `url_key` 与旧档案里的全都对不上，跨 bundle 的去重与「同一页的
历史版本」都拼不起来，而那正是链存在的意义。

所以改名之后**必须重新抓一份全量基准**。代价是一次全量，而改名是罕见事件。

判据缺失（`account` 里没有 `user_id` 或 `username`）时一律不认——「不知道」不是
「是同一个」。

#### 5.5.2 缺口不传染

一份 bundle 自身有缺口，**不影响**它所引用的基准，也不影响链上更早的部分。缺口是
一条关于「这一次抓取」的事实，不是关于整条链的判决。

#### 5.5.3 链是可核对的声明，不是运行时依赖

生产者与消费者都**不得**假定基准 bundle 一定在场。用户会删档案，会只把一部分搬到
另一台机器上。

因此每份 bundle 必须自带足够的信息，让「基准不在了」这件事**可检测**。校验规则，
按路线做：

1. 把链上的 bundle 按 `completed_at` 排序；
2. 对每一份，`floor_time` 必须等于 `floor_from_bundle_id` 那一份里**同一条路线**的
   `high_water_time`；
3. `floor_from_bundle_id` 指向的 bundle 必须在场。

任何一条不成立，就是链上的一处**洞**，**必须**如实报出来。**不得**把缺失的一环当作
连着，也**不得**因此判定在场的那些 bundle 无效——它们各自捕获的东西照样有效，只是
「从今天连续回溯到 X」这句话不再成立。

这与 §5.4 的原则是同一条：缺口必须显式，不得静默。

#### 5.5.4 不得靠复制基准来「保证」链完整

把基准的内容复制进新 bundle 看似能解耦，实际上有两个问题：作品详情页一类的内容占
档案的绝大部分体积，复制等于每次增量都成倍增长；而**同一个 URL 在不同时间的多次
捕获本来就是有价值的数据**（评分变了、短评改了），复制会把「两个版本」混淆成
「同一份数据的两份拷贝」。

正确的做法是上一节：让缺失可检测，而不是让缺失不可能。

#### 5.5.5 没有时间锚的路线不适用增量

作品详情页一类的路线不分页、条目之间没有时间序，`high_water_time` 恒为 null，
`advanced` 恒为 false。对它们「下界」这个概念不成立。

这**不是缺陷**，如实写成 null 即可。这类路线的增量策略属于生产者的选择（例如只抓
本次列表里新出现的条目），**不得**为了让 `advanced` 变成 true 而编一个时间。

## 6. index-\<bundle_id\>.ndjson

每行一个 JSON 对象，对应一次抓取。见 `index-entry.schema.json`。

这是整个 bundle 中**唯一**存放 doubak 专有元数据的地方（§4）。

### 6.1 `url` 与 `url_key`

`url` **必须**是请求时的原始 URL，**逐字节原样保留，包含跟踪参数**（如 `_spm_id`、`_dtcc`）。捕获时**不得**做任何归一化——那些参数本来就是当时那个页面的一部分。

`url_key` 是**索引**：剥除已知跟踪参数、统一尾斜杠后的结果，供去重使用。`url_key_rules` 记录所用规则的版本。

将来发现新的跟踪参数时，可对存量重算 `url_key`，而 `url` 永远不动。**事实与索引并存，索引不覆盖事实。**

### 6.1.1 `final_url`

跟随跳转之后的最终 URL，**仅在与 `url` 不同时出现**。

豆瓣的内容里存在自家的短链（`douc.cc`）。只记下短链，等于在档案里留一个指向
**第三方跳转服务**的死指针——那个服务停掉，这条链接就永远解不开了。记下解析
结果，整条链才在档案内自洽。

它**不替代** `url`：`url` 是请求时的事实，`final_url` 是跟随的结果，两者并存。

### 6.1.2 `item_count` 与 `item_time_range`

都是可选的，都是**抓取时顺手记下的观测**。

`item_count` 是这一页上渲染出来的条目数。生产者判定这一页时本来就要数一遍（`ok` 与
「越界终止页」的区别就在这儿），所以记下来几乎不花成本；而**事后重算要把整条记录取
出来解压、再跑一遍选择器，而豆瓣改版之后那些选择器可能已经对不上了**。

`null` 表示这条路线没有条目概念（如个人主页），**不是 0**。这个区别有意义：0 表示
「数过了，是空的」，而空页正是翻页终点的正常形态。

`item_time_range` 是这一页覆盖的时间区间（`oldest` / `newest`），**不是**抓取时间
（那是 `observed_at`）。两个用处：

1. 不解压任何记录就能看出「第 7 页是哪段时间」——这是人在档案里找东西时的第一个问题。
2. 给下游一个不必重新解析就能排序与对账的依据。

时间**原样保留**豆瓣页面上的形式，**不做时区归一化**。列表页不带时区，归一化就等于
替它假定一个，而假定错了不可恢复（时区假定统一记在 `manifest.timezone_assumption`，
见 §5.2）。

两者都**不是**完整性判据。`item_count` 之和与 `coverage.captured_count` 可能不等——
重复抓取、被打断的页都会造成差异。完整性看的仍然是 `crawl_state` 的连续性证明。

### 6.2 `parent_capture_id`

把这个 URL 放进队列的那次捕获。有了这条链，整张抓取图可以**离线重建**，连续性证明因而可被**第三方独立验证**，而不必信任生产者自己给出的结论。

#### 6.2.1 它可以指向**另一份档案**

`parent_capture_id` 的前缀是 bundle_id，所以它**可以**指向本档案之外的一次捕获。这是合法的，读者**不得**把它当成悬空引用而报错。

这不是理论情形，它由一条真实的生产路径产生：一次增量抓取只取回水位线以上的页面，但从**旧档案里已经存下来的页面**中，仍可能算出当时没有抓的附属资源（正文里的图片、附件）。这些资源理应补抓，而把它们放进队列的那次捕获，客观上就发生在旧档案里。

三种写法只有一种是诚实的：

| 写法 | 问题 |
|---|---|
| 指向旧档案的 capture_id | ✔ 事实如此 |
| `null` | 丢掉来源，等于宣称「凭空冒出来的」 |
| 指向本档案里某次捕获 | **伪造**，而且会污染离线重建出来的抓取图 |

由此得到一个免费的标记：**parent 的 bundle 前缀与本档案不同，本身就说明这条捕获是从既有档案推导出来的，而不是这次从页面上读到的。** 不需要为此新增字段。

读者据此可以：解析得到 bundle_id → 若那份档案在手边就接上，不在就把这条边标成「已知但不可达」。**不可达不等于无效**——用户完全可以在导出后删掉旧档案，这条边仍然如实记录了来源。

### 6.3 `verdict` —— 判定内容，不是状态码

> **豆瓣以 HTTP 200 返回封锁页。只看状态码等于完全没有检测。**

每个响应**必须**得到一个 `verdict`。判定**必须**综合多个信号（见 `vocabularies/verdict.json`），任何单一信号都不足以定论。

- 生产者**必须**把判不出来的响应按失败处理并停下。

#### 6.3.1 `unknown` 与 `verdict_reason`（bundle/1.2）

1.2 之前词表里**没有**「判不出来」这个取值。于是生产者只能退而写 `blocked`，把两件处置正好相反的事合并了：

| | 含义 | 该怎么办 |
|---|---|---|
| `blocked` | 豆瓣主动拒绝了 | 等一等再抓；立刻重试是把限流升级成封号的标准路径 |
| `unknown` | **页面拿到了，只是我们不认识** | 重抓一百次也一样，该做的是**改抽取器** |

实测代价：一篇日记因为没有对应的框架标志判不出来，界面照 `blocked` 显示成「被限制」，用户于是去重试——白费。

**但光有 `unknown` 仍然没用**，它只是把问题换了个说法。所以配套一个开放词表字段 `verdict_reason`，回答「是哪一种判不出来」，因为**处置由原因决定**：

```
empty_body / server_error         → 重抓可能有用
frame_anchors_missing             → 重抓没有用，改抽取器离线重跑即可
url_drifted / unexpected_status   → 先看一眼再决定
```

从原因到处置的映射**由读者推导**，不存进档案——它是解释，而解释应当可以随时重新推导（与「事件是派生视图」同一条原则）。

**`verdict_reason` 是便利索引，不是不可恢复的数据。** 原始字节永远在 WARC 里，重跑一遍分类器就能重新算出原因。所以旧档案没有它并不算受损，也**不必为它重抓**——这一点与 `intent`、`coverage` 那类「丢了就补不回来」的字段性质完全不同，别混为一谈。
- 读者遇到未知 `verdict` 取值时**必须**当作不可信，**不得**当作 `ok`。
- 被判为 `blocked` / `challenge` 的响应**必须**同样写入 WARC——存下来，将来才能不重新抓取就重新训练分类器。

`verdict` 是**封闭词表**：这是安全相关字段，取值拼写错误必须校验失败。这是本规范中对「只增不改」原则的一处**刻意例外**：新增取值会让旧校验器拒绝新 bundle，而对安全字段而言，**响亮地失败优于静默地放行**。

### 6.4 `capture_fidelity` —— 必须诚实

本规范要求「原始字节、原始响应头、不做清洗」。但在浏览器扩展中，`fetch()` **做不到**：它交给调用方的响应体已经解除了 `Content-Encoding`，其响应头对象也是过滤过的——`Set-Cookie` 不可见，原始顺序与大小写均已丢失。

因此每条记录**必须**如实标注自己的成色。

这不是把归档承诺打了折扣——webrecorder 自家的 ArchiveWeb.page 面对同样的限制做了同样的取舍。**真正不可接受的是做不到却宣称做到了**：十年后有人拿这份档案做取证，这个字段就是他判断能信到什么程度的依据。

## 6.5 由实测数据得出的三条强制要求

以下三条来自对一份真实旧档案的检查（见 §5.3），每一条都对应一种**已经真实发生过**的静默数据损坏。

### 6.5.1 空响应必须有 verdict，且不得记为 ok

在那份档案里有两个文件名为 `..._broadcast_p1.html` 的文件，内容其实是**登录页**——会话过期了，抓取工具照样把它按数据文件名写进了磁盘。

要命的是：这两个文件的条目数是 **0**，而同一批次里合法的「翻过最后一页」终止页条目数**也是 0**。二者在文件层面**无法区分**，只能靠体积（16199 vs 19240 字节）和标题。

> 因此：生产者**必须**为每一次抓取写入 `verdict`。**不得**因为「反正内容是空的」而省略。
> 载荷长度为 0 的记录，其 `verdict` **不得**为 `ok`。

### 6.5.2 零长度载荷必须被标记

同一批次里还有 7 个**零字节文件**，与登录页出于同一次会话失效。它们文件名齐全、静静躺在目录里，没有任何东西表明抓取失败过。下游工具只会看到「文件在」。

> 校验器**必须**对载荷长度为 0 而 `verdict` 为 `ok` 的记录报错。

### 6.5.3 不得用声称数量决定翻多少页

旧工具按 `for start := 0; start < claimed_count; start += 15` 决定翻页次数。既然声称数量不可信（§5.3），这个循环在 `claimed < 实际` 时会**静默截断**列表。

> 生产者**必须**依据停滞检测终止翻页，**不得**依据声称数量。

同理，**一页条目数少于分页槽位，不代表这是最后一页**。实测中列表中段的第 7、14、17 页都只渲染出 14、14、13 条。把「短页」当成「末页」会导致列表被拦腰截断。

## 6.6 `surface: asset` —— 图片等二进制资源（bundle/1.1）

图片既不是面向浏览器的 HTML，也不是用于枚举的 JSON 接口，所以它需要 `surface` 的第三个取值。把一份 JPEG 标成 `html` 会让下游按页面去解析二进制，也会让判定逻辑拿结构锚点去判一个**没有结构**的东西。

### 6.6.1 asset 的判定只能看头部与字节数

`verdict` 的一般规则是「判定内容，不是状态码」（§6.3），做法是找页面里的结构锚点。图片没有锚点，所以规则收窄成两条：

> 生产者对 `surface: asset` 的捕获，**必须**在 `verdict` 记为 `ok` 之前确认：
> 1. `Content-Type` 是 `image/*`；
> 2. 载荷长度大于零（§6.5.2 的一般规则在这里同样适用）。
>
> 若请求图片却收到 `text/html`，**不得**记为 `ok`——那几乎必然是封锁页或登录页穿着图片 URL 的外衣回来了。此时按 HTML 的一般规则判定。

这条不是理论上的谨慎：豆瓣以 HTTP 200 返回封锁页是本规范反复处理的既有事实，而图片请求没有理由被豁免。

### 6.6.2 图片走哪个段由「谁上传的」决定，不由「长什么样」决定

段前缀表示留存等级（§2.1），与媒体类型无关：

| 图片 | intent | 段 | 为什么 |
|---|---|---|---|
| 用户自己上传的（相册、广播/日记正文内嵌） | `asset.image.user_upload` | `assets-*` | 神圣。源站删掉就没有了，与用户自己写的文字同级 |
| 作品封面、列表页缩略图 | `asset.image.catalog_thumbnail` | `catalog-*` | 缓存。源站还在就能重抓，可整批丢弃 |

判据是**谁上传的**，不是分辨率或位置。一张出现在广播正文里的作品封面仍然是目录数据；一张出现在作品页上的用户实拍图（若有）仍然是用户上传。分错的后果不是显示问题，而是留存等级错位：用户唯一的照片被归进「可整批删除」的那一堆。

### 6.6.3 图片不参与完整性证明

`crawl_state` 的连续性证明建立在**按时间倒序翻页**之上（§5.4）。图片是从已抓页面派生出来的叶子，彼此之间没有时间序，也没有分页，因此：

> 生产者**不得**为图片路线记录 `high_water_time`，**不得**将 `advanced` 置为 `true`。

读者据此知道：图片的完整性由它所依附的那个页面的完整性担保——页面抓全了，页面上的图就该在；页面本身有缺口，图的缺失只是它的影子，不是另一处独立的缺口。

## 7. checkpoint.json

未完成的 bundle **必须**带 checkpoint。它在抓取期间活在生产者的本地数据库里，**导出时必须一并写入 bundle 目录**——这样一份导出的半成品档案也能被拿到另一台机器上继续抓。

两条容易被忽略的要求：

- **`rate_state` 必须进 checkpoint。** 软封锁之后降了速，恢复抓取时不能把这件事忘掉——忘掉就等于一恢复又按原速撞上去。退避层级设计上只增不减：降速后**不得**自动恢复原速。
- **`pause_reason` 区分停止与暂停。** `session_expired` 是**停止条件**，不可重试；`challenge` / `blocked` 是**暂停**，需人工解决后先以廉价探测确认恢复，再降速续抓。**在软封锁上重试，正是把限流升级成封号的标准路径。**

失败的队列条目**必须**保留在 frontier 中并阻塞该路线推进。跳过失败页会破坏「这条线以上全部已抓」这个不变量。

### 7.1 checkpoint 必须能重建连续性证明，不只是能续上翻页

这一条容易漏，而漏了的后果是**静默的**：抓取照常跑完，manifest 照常写出来，只是里面
每一条路线都写着「被打断、未验证、不许推进水位线」。

连续性证明（§5.4）是这个格式里唯一的完整性依据，而它是**跨越整场抓取**攒出来的：
水位线、已观测的条目 ID、停滞计数、已记录的缺口、这条线走没走完。这些东西在生产者
那里通常活在内存里——而 MV3 的 service worker 每 30 秒空闲就被杀，一场几小时的抓取
必然跨越很多次死亡。

所以 `routes[]` **必须**携带下列字段（`additionalProperties` 允许更多）：

| 字段 | 丢了会怎样 |
|---|---|
| `high_water_time` / `high_water_raw` / `high_water_ids` | 水位线为空 → `advanced` 永远是 false → **增量抓取永远不可能** |
| `low_water_time` / `low_water_raw` | 「已回溯到」清零，界面上的进度倒退 |
| `seen_ids` | 停滞检测失忆：重抓的那一页被整页当成新条目，`items_seen` 虚高，终止推迟 |
| `stall_counter` | 同上，终止条件重新数 |
| `gaps` | **恢复之后重新声称自己是连续的**——即最坏的一种错：假的完整性声明 |
| `finished` / `stopped` | 收尾时无从判断这条线是走完了还是被打断了，只能一律记成打断 |
| `claimed` | 声称数量来自一次性的入口页，重抓不回来 |

判据很简单：**恢复之后产出的 manifest，必须与「一次不间断跑完」产出的那份一致。**
做不到就说明 checkpoint 漏了东西。

反过来也要说清：这些字段是**恢复用的工作状态**，不是档案的一部分。抓取干净结束时
`checkpoint.json` 应当消失（§3.1），证据的最终归宿是 manifest 的 `crawl_state`。

### 7.2 `last_capture_id` 与「派生出来的活」

捕获**每条落盘**（§8.1），而 checkpoint 通常**攒一批才落一次**（每条都落太贵）。
两者的频率不同，中间就有一个窗口：一条捕获已经进了 index，而 checkpoint 还没见过它。

窗口本身不要紧——重来一遍就是了。要紧的是这条捕获**派生出来的活**：下一页的链接、
列表页上的条目链接、页面上的图片。那些东西通常只活在生产者内存里的队列中，进程一死
就没了。而恢复时 index 会把这条捕获认作「抓过了」，于是：

- 它不会被重取
- 它派生的东西**永远不会再被派生出来**
- 没有任何地方记下这件事

这正是本规范反复要防的那种失败：**永久且不可检测**。覆盖率上只是一个偏小的数字。

因此：

> checkpoint **必须**记录 `last_capture_id`——写此 checkpoint 时**已经写成**的最后
> 一条捕获。
>
> 恢复时，生产者**必须**把 index 中序号大于它的那些捕获视为「派生可能已丢」，并
> **应当**重新抓取其中会派生新工作的那些，使派生重新发生。

`capture_id` 的序号单调递增（§3.2），所以「checkpoint 之后写下了哪些」是**可以精确
算出来**的，不需要猜。

两点补充：

- 记的**必须**是已经写成的那条，不是最后**分配**到的序号。序号先分配后写盘，分配了
  却没写成是正常的（空洞的来源），用分配号会多算一条。
- 重抓会让同一个 URL 在一份档案里出现多次。这是**允许**的（§6.1 只要求 `capture_id`
  唯一），也是刻意的取舍：重复是免费的，空洞是永久的。生产者**应当**给重抓设一个上限
  ——不限量地重抓正是撞上风控的样子——并在触及上限时如实告知用户有多少派生没能恢复。

---

## 8. 写入与恢复

### 8.1 落盘顺序

每完成一次抓取，生产者**必须**按以下顺序写入，且**不得**改变顺序：

```
1. 分配序号
2. 追加 WARC 记录到当前段（独立 gzip member）
3. 追加 index.ndjson 一行
4. 更新状态与 checkpoint
```

先写 index 后写 WARC 会留下**指向不存在记录的索引项**，那比孤儿记录难处理得多。

生产者**应当**在每次抓取后立即落盘，而**不应**攒批——攒批意味着崩溃会丢掉一整批。

### 8.2 崩溃恢复

由于每条记录是独立 gzip member，撕裂的文件尾部总是可检测的。恢复步骤：

1. 扫描当前段尾部，找到最后一条完整的 gzip member；
2. 把段文件截断到该位置；
3. 把 index 截断到与之匹配；
4. 从 checkpoint 继续。

## 9. 摘要与归一化

内容摘要的归一化**只做三件事**：

1. NFC 规范化
2. 去除尾部空白
3. 统一换行符

**不得**折叠简繁，**不得**折叠大小写——那些是**真实的编辑**，折叠掉就再也看不见了。

摘要**应当**逐字段计算，使得「改了评分」不会看起来像「改了评论」。

## 10. 版本与兼容

```
spec_version: "bundle/1.1"
```

- **大版本**：仅当旧读者会**误读**新数据时递增。由于 bundle 会冻结，这个数字理论上应当永远是 1；真要递增，说明设计出了严重问题。
- **小版本**：新增可选字段，或封闭词表新增取值。旧读者继续正常工作。

schema 里 `spec_version` 是 **pattern（`^bundle/1\.[0-9]+$`）而不是 const**。写死成某一个数会两头不是人：写 `bundle/1.0`，则 1.1 一落地，schema 就校验不过它自己所描述的格式；改写成 `bundle/1.1`，则全部既有的 1.0 档案当场变成非法——而它们是**不可重抓的**。

### 10.1 版本历史

| 版本 | 日期 | 改了什么 | 对旧档案的影响 |
|---|---|---|---|
| `bundle/1.0` | 2026-07-28 | 初版 | — |
| `bundle/1.1` | 2026-08-01 | 封闭词表 `surface` 新增取值 `asset`（图片等二进制资源） | 无。1.0 档案仍然合法；1.0 的校验器会拒绝含 `asset` 的新档案，这正是封闭词表的预期行为 |
| `bundle/1.2` | 2026-08-07 | 封闭词表 `verdict` 新增取值 `unknown`；新增可选字段 `verdict_reason`（开放词表） | 无损。1.1 及更早的档案仍然合法——它们把判不出来的响应写成了 `blocked`，那是当时唯一的选择。1.1 的读者会拒绝含 `unknown` 的新档案，这正是封闭词表的预期行为 |
| （不改版本号） | 2026-08-06 | §5.4.3 把「`floor_time` 非 null ⇒ `enumeration` 必须为 `bounded`」写成显式不变量，校验器新增对应检查 | **既有档案可能因此变为不合法**，这是有意的。它拦下的是**自相矛盾**的数据（同一个对象里既说「有下界」又说「整份都枚举过了」），而不是某种旧写法——旧写法从来没有合法过，只是没人拦。实测两份真实增量档案被这条规则拒绝 |

规则：

- 同一大版本内**只增不改**：**不得**复用字段名，**不得**改变已有字段的含义。
- 读者**必须**容忍未知字段，且在重写文件时**不得**丢弃它们。这是「只增不改」得以成立的前提。
- **开放词表**（`intent`、`route_key`）：新增取值不构成版本变更；读者遇到未知取值必须原样保留，不得猜测。
- **封闭词表**（`verdict`、`surface`、`capture_fidelity`）：新增取值为小版本变更，旧校验器会拒绝——对结构性与安全性字段而言这是刻意的（见 §6.3）。

## 11. 与 canonical 的关系

`bundle/` 与 `canonical/` 是**两棵独立版本化的树，生命周期相反**。把它们当成一个格式来设计，是本项目最主要的翻车方式。

| | `bundle/` | `canonical/` |
|---|---|---|
| 谁写 | 抓取工具 | 解析器 |
| 生命周期 | 用户跑过就**冻结** | 随时可改 |
| 为什么 | 不能请人重爬 | 拿 WARC 重跑解析器不要钱 |

`canonical/` **刻意推迟**，理由见 `canonical/README.md`。

## 12. 校验

参考校验器：`validate.py`。

```
python3 validate.py <bundle 目录>
python3 validate.py --tests
```

它分两层：**结构性检查**（无依赖，跨文件一致性）与 **schema 校验**（装了 `jsonschema` 才运行）。

最有价值的是第一层，而且其中大多数**无法**用 JSON Schema 表达：偏移量真的指向一个可解压的 gzip member 吗？`claimed_source` 真的指向一条存在的捕获吗？`advanced` 与 `contiguous` 自洽吗？

`tests/invalid/` 下每个反例都配一份 `EXPECTED.txt` 说明它应该触发什么错误。**反例套件是让规范从一篇文档变成一件真东西的关键**：没有它，没人知道校验器到底拦不拦得住。

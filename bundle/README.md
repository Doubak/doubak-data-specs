# bundle/ —— 抓取工具的产出容器格式

抓取工具（`doubak-extension`）在用户浏览器里把豆瓣页面原样存下来，产出的目录就是一个 **bundle**：标准 WARC + 一份清单 + 一份索引。

**它不止一个生产者。** `doubak-import-adapters` 把第三方抓取工具存下来的页面也转成这个格式——那些工具往往只把响应正文写到磁盘，于是 URL、时间、intent 都要事后重建，而**重建出来的东西必须标明是重建的**（见 [SPEC §6.4.1](v1/SPEC.md)，`capture_fidelity` 为此在 bundle/1.3 多了一个取值）。一份规范能被第二个生产者写出来，本身就是它站得住的证据。

它描述的是**抓取行为**——抓了哪个 URL、为什么抓、抓到的可不可信——而**不描述抓到的内容**。它不需要知道任何豆瓣语义：没有「电影」「评分」「看过」这些概念。理解内容是解析器的事，用的是另一棵树（[`../canonical/`](../canonical/)）。

## 为什么这份规范必须一次做对

bundle 是**不可逆步骤的产物**。用户跑完一次抓取，写下去的东西就是他永远拥有的东西——没法请人家重爬一遍，源站的那一页可能已经不在了。

这和 `canonical/` 正好相反：

| | `bundle/` | `canonical/` |
|---|---|---|
| 谁写 | 抓取工具 | 解析器 |
| 生命周期 | 用户跑过一次就**冻结** | **随时可改** |
| 为什么 | 没法请人家重爬 | 拿已有的 WARC 重跑解析器不要钱 |
| 现在的状态 | 草案 bundle/1.3，**尽快定稿** | [刻意留空](../canonical/README.md) |

**把这两者当成同一个格式来设计，是本项目最主要的翻车方式。**

由此得出这份规范唯一的取舍原则：

> 事后能从 WARC 重新算出来的，都是可选的；事后算不出来的，第一版就必须有。

## 版本

| 版本 | 状态 | 入口 |
|---|---|---|
| [`v1/`](v1/) | 草案，当前 `bundle/1.1` | **[SPEC.md](v1/SPEC.md)** ← 规范性文本，先读这个 |

`v1/` 描述的是**大版本 1 这一整条线**，不是某一个小版本：读者接受任何 `bundle/1.x`，既有的 `bundle/1.0` 档案永远合法。版本历史见 [SPEC.md §10.1](v1/SPEC.md#101-版本历史)。

大版本只在「旧读者会**误读**新数据」时才递增。由于 bundle 会冻结，这个数字理论上应当永远是 1；真要递增，说明设计出了严重问题。小版本增加可选字段，或给封闭词表加取值。

## 目录里有什么

```
v1/
├── SPEC.md                      规范性文本（与 schema 冲突时以本文为准）
├── *.schema.json                JSON Schema 2020-12
├── vocabularies/                intent / verdict / surface / capture-fidelity
├── examples/minimal-bundle/     一个真的能跑通校验的最小 bundle
├── tests/{valid,invalid}/       反例套件，每例配一句「应该报什么错」
└── validate.py                  参考校验器
```

## 快速上手

```sh
cd v1
python3 validate.py examples/minimal-bundle
python3 validate.py --tests
python3 validate.py --integrity-only <bundle 目录>   # 只把「字节坏了」当失败
```

结构性检查无需任何依赖；装了 `jsonschema` 与 `referencing` 后会额外跑 schema 层校验。

**错误分完整性与合规性两类**，退出码分别是 `2` 与 `1`（干净是 `0`）。理由见 SPEC §12.1：bundle 是冻结的，所以合规性错误里有一部分永远修不掉，混在一起会让这个校验器变成没人跑的东西。

例子里的偏移量与摘要都是**实算**的，不是手写的——`examples/make-minimal-bundle.py` 会真的构造出 WARC 记录，校验器也会真的到偏移量处去解压验证。

## 五个丢了就补不回来的字段

细节见 SPEC，这里只作提醒：

| 字段 | 为什么补不回来 |
|---|---|
| `spec_version` | 不知道按哪版规范写的，就无法可靠解读 |
| `coverage` | 页面当时声称的数字，源站一变就再也读不到 |
| `intent` | 一份列表的第 7 页，事后无法区分它当初是「看过」还是「想看」的第 7 页 |
| `surface` | 同一条内容在 HTML 与 API 两面各存一份，不标注就会被当成两次修订 |
| `capture_fidelity` | 这条记录到底是不是原始字节，事后无从判断 |

## 三处最容易用错的地方

- **`coverage` 不是完整性证明。** 豆瓣有多套审查/屏蔽机制，计数有时统计于审查之前、有时之后。实测：同一次抓取里电影分毫不差、游戏差 5 条。规范因此**刻意不提供** `completeness` / `reconciled` 字段——不存在的字段无法被误用。完整性看 `crawl_state`。
- **`enumeration` 决定下游有没有资格推断删除。** `full` 才可以；`bounded` 的路线下界以下根本没看过，缺失无法与「没抓到」区分。
- **`verdict` 要判内容，不是 HTTP 状态码。** 豆瓣以 200 返回封锁页。未知 verdict 必须当作不可信，不得当作 `ok`。

## 要改这份规范的话

`doubak-data-specs` 是一个**真实的跨仓库依赖**，不是一个目录。所以：

1. 同一大版本内**只增不改**——不得复用字段名，不得改变已有字段的含义。
2. 读者必须容忍未知字段，且重写文件时不得丢弃它们。这是「只增不改」得以成立的前提。
3. **规范先落地，生产者和消费者再跟上。** 反过来做，就会出现已经发出去、却不符合任何一版规范的 bundle。
4. 改完跑 `validate.py --tests`；**新增一条不变量，就补一个反例**。反例套件是让规范从一篇文档变成一件真东西的关键。
